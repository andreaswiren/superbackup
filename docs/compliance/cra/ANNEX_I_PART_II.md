# Annex I, Part II — Vulnerability handling requirements

Regulation (EU) 2024/2847, Annex I, Part II. Version 1, for superbackup 0.1.x.
Last reviewed 2026-08-31.

Part II is about the manufacturer's *processes*, not the product's properties.
Article 6(b) requires that *"the processes put in place by the manufacturer
comply with the essential cybersecurity requirements set out in Part II of
Annex I."*

Each of the eight points is quoted, then answered with what actually happens,
who does it, and where it is written down. Status uses the same legend as
[`ANNEX_I_PART_I.md`](ANNEX_I_PART_I.md).

The processes here are those of a single volunteer maintainer. That is stated
in [`SECURITY.md`](../../../SECURITY.md) and in
[`SUPPORT_POLICY.md`](SUPPORT_POLICY.md) rather than dressed up as a security
team, because an unkeepable process commitment is worse than a modest one.

---

## Point (1) — Identify and document vulnerabilities and components; SBOM

> *"identify and document vulnerabilities and components contained in products
> with digital elements, including by drawing up a software bill of materials in
> a commonly used and machine-readable format covering at the very least the
> top-level dependencies of the products"*

**Status: Met, above the floor.**

**Components.** A CycloneDX 1.5 SBOM in JSON and XML, in
[`sbom/`](../../../sbom/), generated by
[`sbom/generate.py`](../../../sbom/generate.py) and never hand-written. It
covers the **full transitive graph**, not the top-level dependencies the
Regulation sets as its minimum: 647 components across the five target triples
that `deny.toml` polices, each with name, version, PURL, licence expression,
author, and the SHA-256 of the published `.crate` archive, plus a dependency
record per component so the graph can be walked.

It also covers the components cargo cannot see, which is the part a
tool-generated SBOM normally gets wrong: **Kopia**, a separate executable
resolved at run time, and the Linux system libraries linked dynamically. They
are declared explicitly in `EXTERNAL_COMPONENTS` in the generator, in one place,
reviewable in a diff.

Both outputs are validated against the official CycloneDX 1.5 JSON schema and
XSD on every CI run, and the build fails on a schema error. Full detail,
including what the SBOM deliberately does not cover, is in
[`SBOM.md`](../SBOM.md).

**Staleness.** `python sbom/generate.py --check` regenerates in memory and fails
if the committed SBOM no longer describes the current `Cargo.lock`, naming the
components that were added or removed. It runs in
[`.github/workflows/sbom.yml`](../../../.github/workflows/sbom.yml) on every push
and pull request that touches a manifest, the lockfile, or `sbom/`.

**Vulnerabilities.** Identified from three streams:

| Stream | Mechanism | Cadence |
|---|---|---|
| Rust dependencies | `cargo deny check advisories` against RustSec | Every push and pull request (`ci.yml`) |
| The SBOM as a whole | Vulnerability scan of the CycloneDX document | Every push to `main`, every release (`sbom.yml`) |
| superbackup itself | GitHub private vulnerability reporting | On report; acknowledged within 5 working days |

Kopia's own advisories are a fourth stream and are **not automated**. See point
(2).

Article 13(24) empowers the Commission to specify the format and elements of the
SBOM by implementing act. If one is adopted with requirements the current
generator does not meet, that is a change to `sbom/generate.py`.

## Point (2) — Address and remediate vulnerabilities without delay

> *"in relation to the risks posed to products with digital elements, address
> and remediate vulnerabilities without delay, including by providing security
> updates; where technically feasible, new security updates shall be provided
> separately from functionality updates"*

**Status: Met as a policy; the "separately from functionality updates" limb is
constrained by the release model.**

### Triage

Severity is assessed against [`THREAT_MODEL.md`](../THREAT_MODEL.md), not against
a CVSS score in isolation. The question is which of the model's guarantees the
finding breaks and what an attacker gains.

| Class | Examples | Target |
|---|---|---|
| **Critical** | Secrets extractable from the sealed vault without the master passphrase; a secret reaching a log, an event, a notification, `argv`, an IPC response or any file outside the vault; another local user reading secrets or driving the IPC endpoint | Fix started same day; released as soon as a fix exists and is tested |
| **High** | Path traversal or a write outside a destination root; privilege escalation via the service installer or the autostart entry; a malicious shared-config repository changing local behaviour without the documented decrypt-and-verify step | 7 days to a released fix |
| **Medium** | A crash, hang or memory exhaustion triggerable by malformed input — a corrupt vault, hostile kopia output, a hostile IPC client | 30 days |
| **Low** | Everything else in scope | Next release |

These are targets, not guarantees. [`SECURITY.md`](../../../SECURITY.md) states
plainly that this is a personal open-source project rather than a funded
programme and that timelines depend on maintainer availability. That sentence is
the honest version of a service level, and it is not withdrawn here.

Scope — what is and is not a vulnerability — is defined in `SECURITY.md` and by
§3 of the threat model. The exclusions matter and are not quietly widened here:
malware already running as the user with the vault unlocked, attacks requiring
administrator or physical access, a user choosing a weak passphrase, and the
fact that `LocalMirror` destinations are unencrypted are all out of scope and
documented as such.

### Dependency vulnerabilities

This is where most findings will come from, so the policy is explicit.

1. **A RustSec advisory fails CI immediately.** `deny.toml` sets
   `[advisories] ignore = []` and `yanked = "deny"`. There is no warning state.
2. **The first response is to upgrade.** `cargo update -p <crate>` to a patched
   version, verify the workspace still builds and tests pass on all three CI
   platforms, regenerate the SBOM, release.
3. **Where no patched version exists**, the options in order are: replace the
   dependency; vendor a minimal fix and upstream it (Article 13(6) requires
   reporting the vulnerability to the component's maintainer and sharing the fix
   where one has been developed); or, if the vulnerable code path is
   demonstrably unreachable from superbackup, record a time-boxed exception.
4. **An exception is written down or it does not exist.** It goes in
   `deny.toml`'s `[advisories] ignore` list with the advisory ID, a one-line
   reason stating why the path is unreachable, and a review date. An empty
   `ignore` list is the current state and the intended steady state. A silent
   suppression — pinning an old version, disabling the check for a run — is
   treated as a defect.
5. **A vulnerability in a dependency that is reachable and unfixable is a
   release blocker,** not a known issue.

### Kopia

Kopia is a separate program, and its security posture is superbackup's — that
is stated in [`THREAT_MODEL.md`](../THREAT_MODEL.md) §7 rather than glossed.
Vulnerabilities in Kopia are reported to
[the Kopia project](https://github.com/kopia/kopia/security), not here;
`SECURITY.md` says so, and asks for a heads-up so the minimum supported version
can be raised.

The mechanism for acting on one is `MINIMUM_KOPIA_VERSION` in
`crates/core/src/kopia/binary.rs`: raising it makes superbackup refuse to drive
an affected build, with a message telling the user what to do, and the installer
refuses a release below the configured minimum
(`a_release_below_the_configured_minimum_is_refused`) and below the hard floor
however the settings are written
(`a_release_below_the_hard_floor_is_refused_however_the_settings_are_written`).

**This is a manual step and there is no automated watch on Kopia's advisories.**
Recorded as a gap in [`CONFORMITY_CHECKLIST.md`](CONFORMITY_CHECKLIST.md), with
the plan to subscribe to Kopia's security advisories and add a scheduled CI job
that fails if the pinned floor is below the newest Kopia release carrying a
security fix.

### Security updates separate from functionality updates

During 0.x, only the latest release receives security fixes
([`SECURITY.md`](../../../SECURITY.md), "Supported versions"), which means a
security fix ships in whatever release comes next. On a patch release that is a
security-only release in practice. On a minor release it is not.

From 1.0, the intent is semantic-versioned patch releases cut from the release
branch containing the fix and nothing else, so that a user can take a security
update without taking a feature. That is a commitment about 1.0, stated here so
it can be held to, and it is in the checklist.

## Point (3) — Effective and regular testing and review

> *"apply effective and regular tests and reviews of the security of the product
> with digital elements"*

**Status: Partial.**

**What runs on every push and pull request** (`.github/workflows/ci.yml`):

| Check | Coverage |
|---|---|
| `cargo test --workspace --all-features` | On Windows, Linux and macOS |
| `cargo clippy --workspace --all-targets --all-features` | With `RUSTFLAGS: -D warnings` |
| `cargo fmt --all -- --check` | |
| `cargo deny check` | Advisories, licences, bans, sources |
| MSRV check | `cargo check` on 1.82.0 |
| Cross-compile check | `x86_64-pc-windows-msvc` and `aarch64-apple-darwin` `cfg` gating |
| SBOM freshness, schema validation and vulnerability scan | `sbom.yml` |

**The security-relevant tests are named as such and are adversarial**, which
matters more than a coverage number. The test suite contains, among others:
`a_tampered_header_breaks_decryption_rather_than_being_accepted`,
`a_bit_flipped_ciphertext_is_rejected`,
`a_hostile_header_cannot_make_us_allocate_gigabytes`,
`the_sealed_file_contains_no_plaintext_secret_and_no_plaintext_config`,
`secrets_never_reach_argv` and `the_audit_catches_a_secret_placed_in_argv`,
`there_is_no_request_that_reads_a_secret_back`,
`a_passphrase_never_appears_in_debug_output`, `outbound_frames_are_scrubbed`,
`an_oversized_line_is_refused_without_buffering_it`,
`requests_are_rate_limited_per_connection`,
`a_pull_with_the_wrong_passphrase_never_reaches_the_disk`,
`pinning_a_signer_fails_closed_in_a_build_that_cannot_verify`,
`a_checksum_mismatch_refuses_to_install_and_leaves_nothing_behind`,
`a_zip_slip_archive_is_rejected`,
`a_download_redirected_off_github_is_refused`,
`a_binary_that_lies_about_its_version_is_not_installed`.

Each of those is a security property expressed as an executable assertion. A
regression that removes a control fails the build, which is the only form of
security documentation that cannot rot.

**Review.** [`THREAT_MODEL.md`](../THREAT_MODEL.md) §9 defines when the model is
reviewed: when the crypto design changes, when a new destination kind or
credential type is added, when the IPC surface gains a request returning
sensitive data, and at each minor release. [`CONTRIBUTING.md`](../../../CONTRIBUTING.md)
carries the contribution rules.

**Gaps, stated plainly:**

- **No fuzzing.** The parsers that consume hostile input — the vault envelope,
  Kopia's JSON progress and manifest output, the IPC line protocol — are
  covered by hand-written adversarial tests, not by a fuzzer. `cargo-fuzz`
  targets for `crypto::envelope`, `kopia::progress`, `kopia::manifest` and
  `ipc::codec` are the plan.
- **No independent security review.** Nobody outside the project has audited
  the cryptographic design or the IPC boundary. For a product holding
  repository encryption keys that is a material limitation, and users should
  weigh it.
- **No code coverage measurement**, so "effective" is asserted from the shape
  of the tests rather than measured.
- **No dependency update automation** (Dependabot or Renovate), so dependency
  currency depends on the maintainer running `cargo update`.

All four are in [`CONFORMITY_CHECKLIST.md`](CONFORMITY_CHECKLIST.md).

## Point (4) — Public disclosure of fixed vulnerabilities

> *"once a security update has been made available, share and publicly disclose
> information about fixed vulnerabilities, including a description of the
> vulnerabilities, information allowing users to identify the product with
> digital elements affected, the impacts of the vulnerabilities, their severity
> and clear and accessible information helping users to remediate the
> vulnerabilities …"*

**Status: Met by process; not yet exercised.**

Every fixed vulnerability is published as a **GitHub Security Advisory** on the
repository, which is the mechanism `SECURITY.md` already directs reporters to
and which assigns a GHSA identifier, requests a CVE where appropriate, and
publishes machine-readable affected-version ranges that automated tooling can
consume.

Each advisory carries: a description of the vulnerability; the affected
versions and the first fixed version; the impact, expressed in the terms of the
threat model — what an attacker gains and what access they need to start, which
is exactly what `SECURITY.md` asks reporters to supply; a severity, assigned
using the classes in point (2) above; and the remediation, which for a
single-binary desktop tool is normally "upgrade to version X", with an interim
mitigation where one exists.

The same information appears in `CHANGELOG.md` under the release that carries
the fix, with a link to the advisory. Reporters are credited in the advisory and
the changelog unless they prefer otherwise.

**On the permitted delay.** Point (4) allows a manufacturer to delay publication
where *"the security risks of publication outweigh the security benefits"*,
until users have had the chance to patch. superbackup's disclosure policy is
coordinated disclosure: a fix ships before details are published, and the date
is agreed with the reporter. The one exception, already stated in
`SECURITY.md`, is that **if a vulnerability is being exploited, mitigation
guidance is published immediately rather than waiting for a fix** — which is
also what Article 14 assumes a manufacturer will do.

**Not yet exercised** because no vulnerability has been reported. That is a
statement of fact, not a claim of quality.

## Point (5) — A coordinated vulnerability disclosure policy

> *"put in place and enforce a policy on coordinated vulnerability disclosure"*

**Status: Met.**

The policy is [`SECURITY.md`](../../../SECURITY.md) in the repository root, where
GitHub surfaces it in the Security tab and in the "Report a vulnerability" flow.
It states:

- **The channel**: GitHub private vulnerability reporting, which creates a
  private advisory visible only to the maintainer. Explicitly not a public
  issue.
- **What to include**: what an attacker gains and what access they need to
  start; the affected version and platform; reproduction steps or a proof of
  concept; anything already known about the fix.
- **Response times**: acknowledgement within 5 working days, assessment within
  10.
- **What happens next**: the reporter is kept informed until a fix ships, and is
  credited in the advisory and the changelog unless they prefer otherwise.
- **Scope**: what is in scope, tied to the guarantees in the threat model, and
  what is out.
- **The disclosure model**: coordinated, with a date agreed with the reporter,
  and immediate mitigation guidance if a vulnerability is being exploited.
- **The limits**: no bug bounty, timelines depend on maintainer availability.
- **Safe harbour, in substance**: "We will not ask you to sign anything to
  report a bug, and we will not treat a good-faith report as a hostile act."

Article 13(8), final subparagraph, requires manufacturers to have *"appropriate
policies and procedures, including coordinated vulnerability disclosure
policies … to process and remediate potential vulnerabilities … reported from
internal or external sources."* `SECURITY.md` is the policy; points (2) and (4)
above are the procedure.

## Point (6) — Facilitate information sharing about potential vulnerabilities

> *"take measures to facilitate the sharing of information about potential
> vulnerabilities in their product with digital elements as well as in
> third-party components contained in that product, including by providing a
> contact address for the reporting of the vulnerabilities discovered in the
> product with digital elements"*

**Status: Met, with one thing to wire.**

**The contact address** is GitHub private vulnerability reporting on
`github.com/andreaswiren/superbackup` (Security → Report a vulnerability). It is
in `SECURITY.md`, and it is where GitHub's own UI sends anyone who looks. It is
a single point of contact in the Annex II point 2 sense, and it is the same one
that document names.

**Third-party components.** The SBOM is the mechanism: it is published with
every release, machine-readable, and complete enough that a third party can
determine whether a component they have found a vulnerability in is present, in
which version, and on which platform — the `superbackup:targets` property on
each component answers the last question directly.

**Reporting upstream.** Article 13(6) requires a manufacturer who identifies a
vulnerability in a component to report it to that component's maintainer and
share any fix. The routes are recorded in
[`THIRD_PARTY.md`](../THIRD_PARTY.md); for Kopia specifically,
`SECURITY.md` names the Kopia security page.

**To wire:** the single point of contact and the link to this policy are not yet
in the product itself. The About screen (`design/UX_SPEC.md` §13) currently
specifies licences and links but no security contact. See
[`ANNEX_II_USER_INFORMATION.md`](ANNEX_II_USER_INFORMATION.md), point 2.

## Point (7) — Mechanisms to securely distribute updates

> *"provide for mechanisms to securely distribute updates for products with
> digital elements to ensure that vulnerabilities are fixed or mitigated in a
> timely manner and, where applicable for security updates, in an automatic
> manner"*

**Status: Partial.**

**For the Kopia component — met, and the design is the reference for what the
rest should look like.** `crates/core/src/kopia/install.rs` implements a
verification chain that is documented in the module header and tested end to end
against a local HTTP server in `crates/core/tests/kopia_install.rs`:

```
api.github.com/repos/kopia/kopia/releases/latest      TLS, rustls
      ↓  release JSON: tag, prerelease flag, asset list
checksums.txt from the same release                   TLS, host-checked
      ↓  "<sha256>  <filename>", one line per asset
kopia-<version>-<platform>.<zip|tar.gz>               TLS, host-checked
      ↓  SHA-256 over the bytes actually received, compared against the
      ↓  line for this filename
extract exactly one member named kopia/kopia.exe      path-traversal guarded
      ↓
write to a temp file beside the target, chmod +x, run --version
      ↓
rename into place only if it reports the version the release promised
```

Every link is enforced and every link has a test that breaks it: a checksum
mismatch installs nothing and leaves nothing behind; a release with no checksum
file is refused; a zip-slip archive is rejected; a redirect off GitHub is
refused by the redirect policy itself, so no request is ever issued to the
foreign host; a downgrade is refused; a binary that reports a different version
than the release promised is not kept.

Failure is designed to degrade rather than block: no network, a captive portal,
a corporate proxy, a GitHub outage, an API rate limit or a read-only install
directory all resolve to "carry on with the kopia we already have, and say so".

**The stated limit.** `checksums.txt.sig` is published by Kopia but the signing
key is not available in a form the installer can pin, so the signature is not
verified. The checksum proves the download matches what that release published;
it does not prove who published it. Authenticity rests on TLS to `github.com`
and on GitHub itself, which is why
[`THREAT_MODEL.md`](../THREAT_MODEL.md) §3 places a compromise of the Kopia
project or of GitHub out of scope, and §A8 argues the whole chain.
`InstallOutcome::signature_verified` is always `false` and is recorded in the
event log, so an installation carries its own honest provenance record.

**For superbackup itself — gap.** There is no update distribution mechanism at
all, because there is no release build pipeline: `ci.yml` builds and uploads
per-run artefacts with a 14-day retention but does not publish signed release
binaries, and there is no `release.yml`. Consequently:

- no signed release artefacts,
- no Authenticode signature on Windows, no notarisation on macOS,
- no checksum file published with releases,
- no package-manager presence (winget, Homebrew, distribution packages),
- and therefore no automatic security update path.

This is the single largest process gap in Part II, and it compounds the Part I
point (2)(c) gap. The plan, in
[`CONFORMITY_CHECKLIST.md`](CONFORMITY_CHECKLIST.md), is a release workflow that
builds per-platform binaries, publishes a `SHA256SUMS` file, signs Windows and
macOS builds, produces SLSA build provenance with
`actions/attest-build-provenance`, and binds the SBOM to those binaries with
`actions/attest-sbom` — the last two of which
[`.github/workflows/sbom.yml`](../../../.github/workflows/sbom.yml) is already
written to do the moment binary assets exist on a release.

## Point (8) — Disseminate security updates without delay and free of charge

> *"ensure that, where security updates are available to address identified
> security issues, they are disseminated without delay and … free of charge,
> accompanied by advisory messages providing users with the relevant
> information, including on potential action to be taken"*

**Status: Partial.**

**Free of charge — met, unconditionally.** superbackup is MIT-licensed with no
paid tier, no support contract and no monetisation of any kind. Every release,
including every security release, is free to everyone. This is also the fact on
which the applicability analysis in [`README.md`](README.md) turns.

**Without delay — met as a policy.** The triage targets in point (2) apply, and
a security fix is released as soon as it exists and is tested rather than being
held for a release train.

**Accompanied by advisory messages — met for the published record, gap in the
product.** The GitHub Security Advisory and the `CHANGELOG.md` entry carry the
description, severity, affected versions and remediation. What does not exist is
any in-product notification: superbackup never tells a running installation that
a security update is available, because it has no update check
([`ANNEX_I_PART_I.md`](ANNEX_I_PART_I.md), point (2)(c)).

**Dissemination — gap.** Same root cause as point (7): with no release pipeline
and no package-manager presence, "disseminated" currently means "a git tag
exists". Fixing point (7) fixes this.

## Summary

| Point | Requirement | Status |
|---|---|---|
| (1) | Identify and document components and vulnerabilities; SBOM | Met, full transitive graph rather than top-level |
| (2) | Address and remediate without delay; separate security updates | Met as policy; separation constrained until 1.0 |
| (3) | Regular security testing and review | Partial — no fuzzing, no external audit, no coverage measurement, no dependency update automation |
| (4) | Publicly disclose fixed vulnerabilities | Met by process, not yet exercised |
| (5) | Coordinated vulnerability disclosure policy | Met — `SECURITY.md` |
| (6) | Facilitate information sharing; contact address | Met; contact not yet surfaced in the product |
| (7) | Secure update distribution | Partial — met for Kopia, absent for superbackup itself |
| (8) | Disseminate updates without delay, free of charge, with advisories | Partial — free and prompt, but no dissemination pipeline and no in-product advisory |

Every Partial and Gap appears in the consolidated list at the end of
[`CONFORMITY_CHECKLIST.md`](CONFORMITY_CHECKLIST.md).
